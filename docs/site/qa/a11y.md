# HandSolved accessibility audit, WCAG 2.2 AA

Audited 2026-11-01 against the live static site at `http://127.0.0.1:4321` with the real CSP (meta tag, no bypass; axe was injected with `page.evaluate`, and style tweaks were made through CSSOM only). Browser: Chrome via Playwright, 375 px and 1280 px wide (plus 320, 390 and 640 for reflow and focus checks). Pages: `/`, `/gto-hand-review`, `/live-poker-hand-recorder`, `/privacy`, `/terms`, and an unknown URL (404). Both dialogs and the mobile menu were audited open.

No code was changed. `motion.css` was being finished by another agent, so motion results describe the state at test time and are not weighted heavily.

## A11Y-01 HIGH: the fixed mobile CTA bar completely hides focused controls

- **WCAG**: 2.4.11 Focus Not Obscured (Minimum), Level AA (new in 2.2).
- **Where**: `src/styles/global.css:13` sets only `scroll-padding-top`. There is no bottom equivalent for the fixed bar in `src/components/MobileCtaBar/MobileCtaBar.css:4-15` (`position: fixed; inset-block-end: 0`, about 81 px tall plus the safe-area inset). `src/styles/tokens.css:237` defines `--scroll-pad` for the top only.
- **Problem**: once the hero button has scrolled away, the bar slides up over the bottom of the viewport. A control that is already inside the viewport but under the bar is focused without any scroll, so the focus ring and the control are entirely hidden. Chrome only scrolls when the control is off screen.
- **Verified**: Tab walk of `/` with the bar visible, checking `elementFromPoint` on a 6x6 grid inside each focused control:
  - 375x812: "Do I need to install anything?" (FAQ summary, y 730-786, bar top 731, so all but 1 px is covered) and "Can I export or import my data?" (y 756-812) are hidden. The Numbers chart and the Toolbox tab panel are partly covered.
  - 320x568: 6 stops fully hidden: the "Dollars" switch, "View data as a table", the pricing radio, and three FAQ summaries.
  - 390x664: 3 stops fully hidden: the "Big blinds" switch, "View data as a table" and a FAQ summary.
  - At 200% text size the bar grows to 161 px and the header to 128 px, together 36% of an 812 px viewport, so it gets worse.
  - Shift+Tab upward and the 1280 px layout are clean (the header is handled by `scroll-padding-top`).
- **Reproduce**: open `/` at 375x812, press Tab repeatedly past the hero (the bar appears once the hero button is off screen), keep going to the FAQ. The focused summary at the bottom of the screen is invisible. Script: section A of `scratchpad/a11y/misc.mjs`.
- **Fix** (not applied, re-run the script to confirm): pad the scrollport by the bar height while the bar is shown, so the browser scrolls covered controls into view.

  ```css
  /* MobileCtaBar.css */
  :root {
    --bar-pad-y: calc(var(--space-sm) + var(--space-xs));
    --mobile-bar-h: calc(var(--control-h-lg) + var(--bar-pad-y) + max(var(--bar-pad-y), env(safe-area-inset-bottom)) + var(--border-hair));
  }
  @media (max-width: 47.99rem) {
    html:has(.mobile-bar[data-visible]) {
      scroll-padding-bottom: calc(var(--mobile-bar-h) + var(--space-sm));
    }
  }
  ```

  Remove the local `--bar-pad-y` on `.mobile-bar` so there is one definition. Expected result: zero "FULLY HIDDEN" stops at 375x812, 320x568 and 390x664.

## A11Y-02 MEDIUM: BB/$ buttons fail Label in Name

- **WCAG**: 2.5.3 Label in Name, Level A (axe `label-content-name-mismatch`, impact serious).
- **Where**: `src/components/UnitSwitch/UnitSwitch.astro:26-27` (`aria-label={unitSwitch.bb.name}` / `usd.name`), names defined in `src/data/site.ts` (`unitSwitch`).
- **Problem**: the visible text is "BB" and "$", the accessible names are "Big blinds" and "Dollars". Neither contains the visible text, so a voice-control user saying "click BB" or "click dollar" cannot target them. Appears on `/` in the Highlights switch, the Numbers switch and the sample dialog header (6 buttons per page load).
- **Reproduce**: axe on `/` at any width, or read the button names in DevTools Accessibility. Script: `scratchpad/a11y/axe-run.mjs`.
- **Fix**: drop the `aria-label` and use a name that begins with the visible text.

  ```astro
  <button class="unit-switch__btn" type="button" data-set-unit="bb" aria-pressed="true">BB<span class="visually-hidden">, big blinds</span></button>
  <button class="unit-switch__btn" type="button" data-set-unit="usd" aria-pressed="false">$<span class="visually-hidden">, dollars</span></button>
  ```

  `.visually-hidden` is absolutely positioned, so the grid centring of the label is unaffected. Names become "BB, big blinds" and "$, dollars".

## A11Y-03 MEDIUM: choosing an in-page link in the mobile menu sends focus back to the burger

- **WCAG**: 2.4.3 Focus Order, Level A.
- **Where**: `src/components/Navbar/Navbar.ts:122-129`, the `close` handler (`toggle.focus()` at line 128) runs for every way the menu closes, including a link.
- **Problem**: after "How it works" or "Pricing" is activated from the menu, the page scrolls to the section but focus is on `#nav-toggle`. The next Tab goes to the first control of the hero, which scrolls the page back up. Keyboard, switch and screen-reader users lose their place and must tab through the page again.
- **Verified**: 375 px, Tab to "Open menu", Enter, focus "How it works", Enter. Result: `location.hash` is `#how`, menu closed, `document.activeElement` is `#nav-toggle`, scrollY 1305. Next Tab: hero "Grade a sample hand", scrollY 269. Esc and the X correctly return focus to the burger.
- **Reproduce**: script `scratchpad/a11y/dialogs.mjs 375` (T2).
- **Fix**: leave focus alone when the close came from a link, so the browser's fragment navigation keeps the sequential focus start point at the target.

  ```ts
  let viaLink = false;
  menu.addEventListener('click', (e) => {
    const hit = e.target instanceof Element ? e.target.closest('[data-nav-close], a[href]') : null;
    if (!hit) return;
    viaLink = hit.matches('a[href]');
    close();
  });
  menu.addEventListener('close', () => {
    delete menu.dataset.state;
    if (viaLink) { viaLink = false; return; } // the link's target now owns the reading position
    if (!document.querySelector('dialog[open]')) toggle.focus();
  });
  ```

  Re-test: after the menu closes, the next Tab should land on the first control inside `#how`. If a target has no focusable child, give the section `tabindex="-1"` and focus it with `preventScroll: true`.

## A11Y-04 MEDIUM: the preflop range chart has no text equivalent of its 169 cells

- **WCAG**: 1.1.1 Non-text Content (A), with 1.4.1 Use of Color (A) as a contributing factor.
- **Where**: `src/assets/svg/chart-bb-vs-btn-100.svg` (`role="img"` plus a summary `aria-label`), used in `src/sections/home/Engine.astro:68` and `src/sections/gto-hand-review/WhatYouSee.astro:96`.
- **Problem**: the label gives totals ("folds 48.5%, calls 38.8%, raises 12.7%") and "the strongest hands at the top left are red", but which hand raises, calls or folds, and which are mixes, exists only as cell colour. Children of `role="img"` are presentational, so a screen-reader user cannot read a single hand. The bankroll chart has a data table; this chart has none. For sighted users raise vs call is red vs black with no pattern or glyph. Measured luminance contrast red/black is 3.25:1 (normal vision) and 2.23:1 simulated protanopia (Machado 2009), under the 3:1 needed to count as more than colour.
- **Verified**: DOM and AX name of the SVG, the caption text, pixel sampling of `shots/hc-full.png`. Grade chips are not affected (icon, text label and border style all differ).
- **Reproduce**: open `/gto-hand-review`, Range grids tile. Inspect `svg.hc-full`: one `aria-label`, no table, no list.
- **Fix**:
  1. Add a "View the chart as a list" `<details>` under each figure, using the same pattern as `Numbers.astro` ("View data as a table"), generated at build from `src/data/range-chart.json` (`f` is `[fold, call, raise]`). Group by action: "Always raise", "Raise or call" with percentages, "Always call", "Call or fold", "Fold: every other hand".
  2. Give call a second, non-colour cue in `src/assets/svg/chart.css` and the legend swatch `.engine__swatch--call` (a diagonal hatch fill or a corner dot), and mention it in the `engine__read` caption.

## A11Y-05 LOW: page BB/$ buttons are 36 px tall, below the 44 px mobile target

- **WCAG**: 2.5.8 Target Size (Minimum), Level AA is met (24 px). This is below the project's own 44 px rule for key mobile controls (and the WCAG 2.5.5 AAA size).
- **Where**: `src/components/UnitSwitch/UnitSwitch.css:5-7,29-30,93-99`. The track is 44 px but padding (3 px) and border (1 px) leave 40x36 buttons; the `::after` hit-area extension exists only for `.unit-switch--compact`.
- **Verified**: measured 40x36 at 375 and 1280 with only 1 px of extra hit area. The compact dialog switch is 40x28 but its extension gives about 45 px effective, so it is fine.
- **Reproduce**: script `scratchpad/a11y/misc2.mjs` (section D).
- **Fix**: apply the extension to every switch.

  ```css
  .unit-switch__btn::after { content: ''; position: absolute; inset-block: calc(var(--space-xs) * -1); inset-inline: 0; }
  ```

  Remove the `.unit-switch--compact` selector from that rule, but keep the compact rule's larger extension (`-8px` gives 28+16=44).

## A11Y-06 LOW: the BB/$ announcement is written to a live region outside the open modal

- **WCAG**: 4.1.3 Status Messages (AA). Partly mitigated: the focused button's `aria-pressed` changes, which most screen readers announce.
- **Where**: `src/components/UnitSwitch/UnitSwitch.ts:47-60` (a `p[role=status]` appended to `body`, text set at line 60).
- **Problem**: while the sample dialog is open (it has its own BB/$ switch in the header) everything outside the modal is dropped from the browser accessibility tree. Verified through CDP `Accessibility.getFullAXTree` with the dialog open and the switch pressed: the dialog's own `[data-live]` status node is in the tree (not ignored), the body-level `p[role=status]` that receives "Amounts now shown in dollars." is not in the tree at all, so the message cannot be exposed.
- **Reproduce**: open the sample dialog, press a BB/$ button, then compare the two status nodes in `Accessibility.getFullAXTree`. Script: `scratchpad/a11y/ax2.mjs`.
- **Fix**: speak into the dialog's own region when a dialog is open.

  ```ts
  const speak = (text: string) =>
    (document.querySelector<HTMLElement>('dialog[open] [role="status"]') ?? status).textContent = text;
  ```

  Call `speak(unitSwitch[unit].announce)` at line 60. Note `SampleHandDialog.ts` overwrites the same region for what-if rows, which is harmless.

## Not verifiable without a real screen reader

I could verify DOM, attributes, the Chrome accessibility tree and focus, not what is spoken.

1. Whether a hand pick is actually announced well: focus moves to `h3#hs-vh` with `aria-describedby`, and the `role=status` region only speaks on what-if changes. Support for the description on focus, order and double announcements differs between NVDA, JAWS and VoiceOver.
2. The bankroll chart: `role="img"` with `tabindex="0"` and arrow keys. In NVDA and JAWS browse mode the arrow keys may be consumed by the reader and never reach the chart. If so, a `role="slider"` with `aria-valuetext` is the robust pattern. The data table is the fallback today.
3. `<h3>` inside `<summary>` (all FAQs, Engine "Plain words"): some reader and browser pairs flatten heading semantics inside summary.
4. The early-access dialog sets `role="alert"` or `role="status"` at the same moment it sets the text (`EarlyAccessDialog.ts` `paint()`), which is unreliable for the hint and the blur case; a pre-existing live region is safer.
5. Speech and voice-control behaviour of the BB/$ names, and of the pressed state after A11Y-06.
6. Skip-link focus target: `<main id="main">` has no `tabindex="-1"`. Chrome moves the sequential focus point anyway; Safari and Firefox were not tested.
7. Toolbox tab auto-activation announcements, and the reading order of the pinned scroll story in `#how`.
8. iOS Safari and Android: real touch, Dynamic Type, VoiceOver and TalkBack. Forced-colours mode and Safari were not run.
